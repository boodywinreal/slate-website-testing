Slate Linux

System documentation · Release 0.6

A lightweight Linux distribution built around musl, simple userspace tools, and a custom package management system.

01. Introduction
What is Slate?

Slate is an independent Linux distribution targeting x86_64 systems using the musl C library.

The project maintains its own boot process, init system, package manager, and ports collection. The goal is to provide a relatively small and understandable operating system without requiring a large collection of system management dependencies.

Project goals
  • Use musl as the system C library.
  • Keep the base system small.
  • Maintain a simple and understandable init system.
  • Provide an independent package manager.
  • Build software from source using ports.
  • Keep system components relatively independent.
  • Avoid unnecessary dependencies.
  • Provide a straightforward cross-compilation environment.

02. Boot Process and Initramfs
Overview

Slate maintains its own initramfs. It is loaded by the Linux kernel and provides the early userspace environment required to locate and mount the actual root filesystem.

The initramfs is responsible for preparing the basic virtual filesystems, identifying the root device, and transferring control to the installed Slate system.

Initramfs components
ComponentPurpose
init Early userspace entry point executed by the kernel.
toybox Provides basic utilities required during boot.
choose-root Selects or locates the root filesystem.
slate-switch-root Transfers execution to the real root filesystem.
Boot sequence
  1. The bootloader loads the Linux kernel and initramfs.
  2. The kernel initializes hardware and extracts the initramfs.
  3. The kernel executes the initramfs /init.
  4. Slate prepares /dev, /proc, and /sys.
  5. choose-root locates the requested root filesystem.
  6. slate-switch-root transfers control to the installed system.
Kernel command line

Slate uses the ROOT= kernel command-line parameter to identify the root filesystem.

Example:

ROOT=/dev/sda2

A missing or invalid ROOT= parameter prevents the initramfs from selecting the root filesystem.

Virtual filesystems

Early userspace prepares the virtual filesystems needed by the system.

Mount pointFilesystemPurpose
/devdevtmpfsDevice nodes
/procprocKernel and process information
/syssysfsKernel device and hardware information
/runtmpfsRuntime state
03. Slate Init System
Overview

Slate uses its own init system to initialize the installed system after the initramfs has transferred control.

The main initialization script is located at: 

/bin/rc.init
Startup sequence
  1. The real root filesystem becomes active.
  2. /bin/rc.init begins system initialization.
  3. Startup scripts in /etc/init.d/ are processed.
  4. System services are initialized.
  5. Virtual terminal gettys are started.
  6. The system becomes available for login.
Startup scripts

Service startup scripts are stored in: 

/etc/init.d/

Scripts are processed in lexicographical order. This allows their filenames to determine their execution order.

For example:

/etc/init.d/
    00-something
    10-something
    20-something

The exact filenames depend on the installed services.

Boot logging

Slate stores boot output in: 

/var/log/boot.log

This file can be used to investigate startup failures and determine which initialization scripts were executed.

Virtual terminals

Slate provides three virtual terminal login sessions using Toybox getty.

These provide multiple independent text login sessions without requiring a graphical environment.

04. Services
Service layout

System services are managed through startup scripts in /etc/init.d/.

The init system processes these scripts during system initialization.

Core services

Core services provide functionality required for normal system operation. Examples include filesystem setup and basic networking initialization.

Optional services

Optional services provide additional functionality and can be installed separately.

ServicePurpose
sdhcpDHCP networking
filesystemsFilesystem initialization
seatdSeat management
sshdSSH server
Adding services

A service is integrated into Slate through its startup script in /etc/init.d/.

Scripts should be designed to initialize their service and report failures appropriately.

05. Networking
Overview

Slate provides basic networking initialization through its service system.

The networking setup includes loopback initialization and DHCP configuration.

Loopback interface

The loopback interface provides local network communication within the machine. 

lo

It is normally configured with the address 127.0.0.1.

DHCP

Slate includes the sdhcp service for obtaining network configuration through DHCP.

DHCP can provide an IP address, gateway, and other network configuration supplied by the local network.

Network troubleshooting

Useful commands for diagnosing network problems:

ip link
ip addr
ip route
ping 1.1.1.1

Check that the network interface exists, is enabled, has an address, and has a valid route.

06. System Configuration
Configuration directory

Slate stores system-wide configuration under: 

/etc/

This includes service configuration and package manager configuration.

Package manager configuration

Slate package manager configuration is stored under: 

/etc/slate.conf/
Repository configuration

Git-based package repositories are configured in: 

/etc/slate.conf/repos

Each line contains a repository URL followed by the branch to use.

Example:

https://github.com/surprisedcat32/slate-ports.git main
https://github.com/surprisedcat32/slate-ports.git testing

Multiple repositories can be configured. This allows Slate to retrieve ports from separate repositories and branches.

Example repository configuration 
# Main repository
https://github.com/surprisedcat32/slate-ports.git main

# Testing repository
https://github.com/surprisedcat32/slate-ports.git testing

# Community repository
https://github.com/example/slate-community.git main

Repository entries should use the format: 

GIT_URL BRANCH
07. Slate Package Manager
Overview

Slate includes its own package manager for managing software built through the ports collection.

Packages are identified using category/package names. This keeps package names organized and avoids relying on a single flat namespace.

Installing packages

Install a package by specifying its category and name: 

slate install category/package

Example:

slate install x11/dillo
Removing packages

Remove an installed package: 

slate remove category/package
Searching for packages

Search the available package collection: 

slate search package

This can be used to locate a package before installing it.

Listing installed packages

Display packages currently installed: 

slate installed
Package naming

Slate uses the following naming convention: 

category/package

For example: 

x11/dillo
net/curl
utils/less

The category identifies the general type of software, while the package name identifies the individual port.

Repositories

Package definitions are retrieved from Git repositories. Slate 0.6 supports multiple repositories, allowing different collections to be used together.

Repository configuration is stored in /etc/slate.conf/repos.

Each configured repository specifies a Git URL and the branch to use.

Testing repositories

Testing branches can be configured separately from the main repository branch.

This allows experimental ports and package changes to be maintained without immediately placing them in the main collection.

08. Ports Directory Layout
Overview

Slate uses a ports collection to define how software is downloaded, built, staged, and installed.

Ports are stored under: 

/usr/ports/

Each port is maintained in its own directory and contains a port.sh script.

Directory structure 
/usr/ports/
├── dev/
├── lib/
├── meta/
├── misc/
├── net/
├── perl/
├── system/
├── utils/
└── x11/

Each category contains individual package directories.

For example:

/usr/ports/
└── x11/
    ├── dillo/
    │   └── port.sh
    ├── picom/
    │   └── port.sh
    └── xeyes/
        └── port.sh

Port scripts

Every port uses a port.sh file to describe the build process.

The port script defines the operations needed to obtain and build the software, along with the installation staging process.

Port scripts are shell scripts, keeping package definitions relatively simple and readable.

09. Creating and Maintaining Ports
Creating a new port

Create a directory inside the appropriate category and add a port.sh file.

Example layout:

x11/
└── example/
    └── port.sh
Build process

Ports describe how to obtain and compile upstream software and stage the resulting installation.

Build scripts should account for the target architecture, the musl toolchain, and the Slate sysroot.

DESTDIR staging

Software should be staged into a temporary destination rather than directly installed into the build host.

The DESTDIR variable is used by many build systems to control the installation destination. 

make DESTDIR="$DESTDIR" install

This separates the package's installed files from the build environment and allows the package manager to handle the staged files.

Dependencies

Ports may require libraries or other packages to build or run correctly.

Dependencies should be identified and maintained alongside the port definition.

Avoid unnecessary dependencies where possible, especially when maintaining a lightweight base system.

Testing ports

New ports should be built and tested against the intended Slate environment.

  • Check that the source downloads correctly.
  • Check that configuration succeeds.
  • Check that compilation completes.
  • Check that installation stages into DESTDIR.
  • Check that installed files use the expected paths.
  • Test the resulting software on Slate.
Maintaining ports

Ports should be updated when upstream releases change, dependencies change, or build issues are discovered.

Changes should be tested before being placed in the main ports collection.

10. Building Software
Cross-compilation

Slate targets x86_64-linux-musl. Software is cross-compiled using a musl-targeting compiler and the Slate sysroot.

This allows software to be built from a separate Linux build environment without compiling against the host's C library.

Compiler

The target compiler is:

x86_64-linux-musl-gcc

C++ software uses the corresponding C++ compiler: 

x86_64-linux-musl-g++
Sysroot

The sysroot provides the headers and libraries belonging to the target system.

It prevents software from accidentally using host headers or libraries during compilation.

A compiler invocation can specify the sysroot with: 

x86_64-linux-musl-gcc \
    --sysroot=/path/to/sysroot \
    source.c -o program
Build environment variables

Build systems commonly use compiler and installation variables to select the target toolchain and staging destination. 

CC=x86_64-linux-musl-gcc
CXX=x86_64-linux-musl-g++
DESTDIR=/path/to/staging

The exact variables required depend on the upstream project's build system.

Build output

The sysroot build produces a compressed archive: 

archive.tar.xz

This archive can be used to distribute or transfer the resulting system filesystem.

11. Installing Slate
Overview

Slate is assembled as a root filesystem containing its userspace, libraries, configuration, services, and package management tools.

The installation process places this filesystem on the target system and configures the boot process to load the Slate kernel and initramfs.

Root filesystem

The installed system contains the files required for normal operation, including:

  • Essential commands and utilities.
  • musl runtime libraries.
  • System configuration under /etc.
  • Startup scripts under /etc/init.d.
  • Package manager configuration.
  • Installed software and libraries.
Boot configuration

The bootloader must load the Slate kernel and initramfs. The kernel command line must identify the root filesystem using the ROOT= parameter. 

ROOT=/dev/sda2

13. Releasing Slate
Preparing a release

Before publishing a release, changes to the system, package manager, initramfs, and ports collection should be tested.

  • Verify that the root filesystem builds correctly.
  • Verify that the initramfs can boot.
  • Test root filesystem selection.
  • Test service initialization.
  • Test networking.
  • Test package installation and removal.
  • Test important ports.
  • Update the documentation.
Release archive

The build process produces archive.tar.xz, containing the generated system filesystem.

Version control

Slate source code and ports are maintained using Git. Changes should be committed and tested before being included in a release.

Separate development and testing branches can be used to organize work before merging changes into the main branch.

14. Troubleshooting
Root filesystem not found

If the initramfs reports that ROOT= is missing, check the kernel command line.

Inspect it using:

cat /proc/cmdline

Ensure the bootloader supplies the correct root device.

Boot process failures

If Slate fails during startup, inspect the boot log: 

cat /var/log/boot.log

Check which initialization script failed and whether its required programs or dependencies are available.

Networking problems

Check network interfaces, addresses, and routes: 

ip link
ip addr
ip route

Verify that the appropriate networking services have been initialized.

Package build failures

When a port fails to build, check:

  • Whether the source archive or Git repository is available.
  • Whether the required build dependencies exist.
  • Whether the correct cross-compiler is being used.
  • Whether the sysroot contains the required headers.
  • Whether the build system supports the target architecture.
  • Whether installation is correctly staged through DESTDIR.
Missing shared libraries

Check that the required libraries exist in the target filesystem and that the program was built against the correct musl environment.

A program built against the host's glibc environment may not run correctly on Slate.
